## 2. Blocking findings — fix before building

### B1. VND is not a PayPal REST Payouts currency — remove it from the payout path
**Severity: blocking. Affects every doc.**
All four core docs list payout currencies as `USD, EUR, GBP, SGD, VND`
and the SPEC hard-codes VND into the `PayoutItem` type and the
`APIMaticPayoutGuard` allow-list. PayPal's official REST API currency
list is AUD, BRL, CAD, CZK, DKK, EUR, HKD, HUF, ILS, JPY, MYR, MXN, TWD,
NZD, NOK, PHP, PLN, GBP, RUB, SGD, SEK, CHF, THB, USD — **no VND**.
VND appears only in Braintree's currency list, which is a different
product. Vietnam itself is listed for Payouts as "Send, receive, and
withdraw" (not in local currency).
**Fix:** payout currencies become `USD, EUR, GBP, SGD` only. A VND
invoice may be *displayed* and converted to USD for the PayPal call,
with the conversion rate and fee shown — never sent as `currency: VND`.
Update the type, the guard allow-list, the PRD, the overview and the
seed data in one pass. A judge testing a VND payout will get a PayPal
rejection; that is a Stage One failure, not a cosmetic bug.

### B2. Every webhook event name in the docs is wrong
**Severity: blocking. Affects PRD, SPEC, RULE, STRATEGY.**
The docs subscribe to `PAYOUTS.BATCH.SUCCESS`, `PAYOUTS.ITEM.SUCCEEDED`,
`PAYOUTS.ITEM.FAILED`, `PAYOUTS.BATCH.DENIED`. PayPal's actual webhook
event names are `PAYMENT.PAYOUTSBATCH.SUCCESS`,
`PAYMENT.PAYOUTSBATCH.DENIED`, `PAYMENT.PAYOUTSBATCH.PROCESSING`,
`PAYMENT.PAYOUTS-ITEM.SUCCEEDED`, `PAYMENT.PAYOUTS-ITEM.FAILED`,
`PAYMENT.PAYOUTS-ITEM.BLOCKED`. Subscribing to the documented names
means no webhook ever arrives and Feature 4 silently never works.
**Fix:** rename every event in docs and code to the `PAYMENT.*` names.
The SPEC webhook handler also has only a comment where signature
verification belongs ("Verify event header algorithm and signature here
in production"). Implement real verification via PayPal's
Verify Webhook Signature API (`/v1/notifications/verify-webhook-signature`)
with the webhook ID from env — an unverified webhook endpoint that
updates a money ledger is a security finding, not a TODO.

### B3. The AI has no single identity, and FX has no data source
**Severity: blocking for Technological Implementation and Presentation.**
- The overview and PRD name the runtime engine "Muse AI & Muse Code".
  STRATEGY and both Gemini prompts name it "OpenAI GPT-4o + LangChain".
  No doc names one model, one provider, one API key env var, or what
  happens when the model is unavailable beyond "deterministic fallback".
- No doc names any FX rate source. "Real-time FX trends", "volatility
  spreads" and "1.4% more favorable than 7-day average" are asserted
  with no provider (ECB, ExchangeRate-API, Frankfurter, PayPal's own
  conversion quote, etc.), no refresh interval, no cache and no
  fallback when the source is down.
**Fix:** pick ONE runtime AI and write it everywhere: GPT-4o via the
OpenAI API (LangChain optional, not required), `OPENAI_API_KEY` in env.
"Muse Code" is the coding agent that writes the code, not a runtime
component — remove it from the architecture diagram and the stack
table. Name one FX source, pin its endpoint, and define the fallback:
if the FX source or the LLM times out, the advisor returns HOLD with a
rule-based score and never auto-executes.

## 3. Major findings

### M1. Autonomous money movement with no approval gate and no cap
The docs contradict themselves: "autonomous decision engine … triggers
PayPal Payouts" (RULE), "one-click execution" (overview), "batch-approve
with one click" (PRD). No per-batch cap, daily cap, recipient whitelist
or approval step is defined anywhere — unlike a guarded treasury, which
is the whole pitch ("Bảo Vệ Tiền" = protect the money). A judge will
ask what stops the AI from draining the sandbox balance on a bad
recommendation. **Fix:** human approval is mandatory before every
batch; add a per-batch cap and a daily cap (pick numbers, e.g. sandbox
demo cap $500/batch), a recipient allow-list, and an `awaiting_approval`
state for anything over the cap. The AI *recommends*, the human
*approves*, PayPal *executes*. Say that sentence verbatim in the README.

### M2. APIMatic is mischaracterised as a runtime validator
The docs present the APIMatic Context Plugin as a production-path
validator and PII-masking engine. In reality it is a build-time /
coding-agent plugin: it gives the coding agent PayPal OpenAPI context
so generated calls are type-correct. The `APIMaticPayoutGuard` class in
the SPEC is hand-written validation code, not APIMatic output, and
calling it APIMatic is misleading — and APIMatic's co-founder is a
judge. **Fix:** reframe honestly — APIMatic Context Plugin used during
development to generate/verify the Payouts client; runtime validation
is our own guard (rename it `PayoutGuard`). Document the actual
APIMatic usage in a `docs/APIMATIC.md` with the exact calls it helped
write, so the $1,000 sponsor prize claim is auditable.

### M3. The PII-masking code in the SPEC is buggy
`sanitizeForLLM` uses `/(?<=^.{2}).(?=.*@)/g`, which does not mask an
email the way the comment claims, and it masks only `receiver` — not
`note`, `sender_item_id`, or any free-text field that can carry PII.
**Fix:** replace with a deterministic mask (keep first 2 chars + domain,
or hash the local part) applied to every string field before any LLM
call, plus a unit test with a real email. Do not send raw recipient
emails to the LLM at all if the advisor only needs currency, amount
and country.

### M4. AG Grid: Studio vs Community mismatch, trial terms
The overview/PRD promise "AG Grid Studio", but the SPEC code imports
`ag-grid-community` with the old `ag-theme-alpine` CSS — that is the
community grid, not Studio, and the import path is outdated for
current AG Grid versions. The trial licence in the project materials
is evaluation-only, single-application, and time-limited. **Fix:**
decide Studio vs Community and make the code match the claim; use the
current AG Grid import style; never commit any licence key; if the
build uses the trial, say so in the README and keep the demo inside
the trial terms. The AG Grid sponsor prize ($5,000 1st) requires real
use of an AG Grid tool — a community grid with no Studio feature does
not clearly qualify.

### M5. PayPal Payouts needs approval before sandbox testing works
Per PayPal's own AI-Toolkit Payouts reference: Payouts access requires
approval via the Developer Dashboard; prerequisites are a verified
Business account, confirmed email and sufficient balance. Standard
Payouts covers 96 countries and 24 currencies; per-item maximum is
$20,000; rate limit 400 POST/min. **Fix:** request Payouts access on
the sandbox app on day 1 (Nov 7) and prove it with one real sandbox
batch returning 201 + `payout_batch_id` before building the UI. If
approval is pending, that is the critical path — do not build the
dashboard first.

### M6. PayPal Agent Toolkit / MCP is real but narrower than claimed
`@paypal/agent-toolkit` and `@paypal/mcp` (`npx -y @paypal/mcp
--tools=all`) exist, and PayPal's MCP rollout is real. The first MCP
features are invoicing-led; the docs claim the MCP does "conversational
sandbox testing" for Payouts without showing which MCP tool does it.
**Fix:** verify which toolkit/MCP tools actually expose Payouts and
cite them by name; if MCP does not expose Payouts, use the toolkit's
REST tools or a hand-written REST client and say so. Do not claim MCP
coverage that is not in the repo.
